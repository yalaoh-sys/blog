## 먼저 문서부터: PRD 한 장

이 블로그는 코드가 아니라 **문서**에서 시작했습니다. 목표, 사용자 역할, 기능 목록(우선순위 P0~P2), 데이터 모델, 보안 원칙, 마일스톤, 수용 기준, 열린 질문까지 한 장의 PRD에 담았습니다. AI에게 "블로그 만들어줘"라고 말하는 것과 "이 PRD의 M0, M1을 구현해줘"라고 말하는 것은 결과가 전혀 다릅니다. 후자는 완료의 기준이 문서에 이미 있기 때문입니다.

특히 도움이 된 것은 **열린 질문** 목록이었습니다. 캡차는 무엇을 쓸지, 댓글 기본 모드는 무엇인지처럼 아직 정하지 못한 항목마다 *권장안*을 적어 두었더니, 결정을 미루는 질문에는 권장안으로 진행하고 나중에 바꿀 수 있었습니다.

## 계획을 승인한 뒤에 구현하기

구현 전에 AI가 먼저 계획을 작성하게 했습니다. 이 단계에서 이미 중요한 사실이 드러났습니다. 작업 폴더에는 PRD만 있었고, PC에는 Node.js가 설치되어 있지 않았습니다. 코드를 바로 쓰기 시작했다면 중간에 막혔을 문제를 계획 단계에서 발견한 셈입니다.

계획에서 범위도 좁혔습니다. 전체 6개 마일스톤을 한 번에 하지 않고 **M0(기반) + M1(관리자·글)** 까지만 하기로 했습니다. 범위가 작을수록 AI의 결과물을 사람이 검토하기 쉽습니다.

## 키가 없어도 빌드되는 구조

Firebase 프로젝트가 아직 없는 상태였기 때문에, 환경변수가 없어도 빌드가 되고 화면에 안내가 뜨도록 만들었습니다. 이렇게 하면 외부 서비스 연동과 코드 작성을 **병렬로** 진행할 수 있습니다. 그 사이 사람은 콘솔에서 프로젝트를 만들고, AI는 코드와 설정 가이드를 작성했습니다.

## 검증은 실제 환경에서

빌드와 린트가 통과해도 끝이 아닙니다. 이번에는 다음을 직접 확인했습니다.

- 로그인하지 않으면 `/admin`이 로그인 화면으로 이동하는가
- 쿠키 없는 관리 API 호출은 401을 돌려주는가
- 다른 출처(Origin)의 요청은 403으로 막히는가
- 실제 Google 계정으로 로그인한 뒤 카테고리와 글이 저장되는가
- 글을 삭제하면 휴지통으로 이동하고 목록에서 사라지는가

이 중 일부는 AI가 브라우저를 직접 조작해 확인했고, 로그인 팝업처럼 사람이 눌러야 하는 단계는 사람이 맡았습니다. **역할을 명확히 나누는 것**이 협업의 핵심이었습니다.

## 배운 점

1. **문서가 곧 프롬프트다.** 구체적인 PRD가 가장 좋은 지시문이었습니다.
2. **계획 단계에서 막힘을 찾는다.** 환경 문제는 코드를 쓰기 전에 드러나는 편이 훨씬 싸게 해결됩니다.
3. **작게 나눠서 검증한다.** 마일스톤 단위로 자르면 잘못된 방향을 일찍 바로잡을 수 있습니다.
4. **비밀은 사람이 관리한다.** 서비스 계정 키처럼 민감한 값은 채팅에 붙여 넣지 않고 로컬 파일로만 다뤘습니다.
5. **AI의 결과는 증거로 확인한다.** "된 것 같다"가 아니라 실행 결과로 판단했습니다.
